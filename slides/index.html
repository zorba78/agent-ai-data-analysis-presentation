    • 계보: R Markdown(2012)은 R 패키지 rmarkdown + knitr. Quarto(2022)는 같은 팀이 만든 독립 실행 프로그램. Rmd 파일을 qmd로 바꾸지 않아도 Quarto가 그대로 렌더

    • 계속 지원: R Markdown도 유지보수는 계속됨. 새 기능은 Quarto에만 추가
    • 이 사례: 2026-03 분석 보고서부터 qmd. 발표자료도 qmd

Positron + Claude Code vs 웹 Code

2. 작업 환경

  • 대본
    • Claude Code는 웹에서도 쓸 수 있는데, 왜 굳이 Positron 안에서 쓸까요?

    • 그래서 저는 채팅에 적힌 “OR 0.30”이라는 글자를 읽는 대신, 그 모형 객체를 제가 직접 열어서 확인합니다.
    • 물론 설치 없이 바로 시작하고 싶거나 결과만 받으면 되는 작업이라면 웹이 더 낫습니다.
    • 저는 분석이 중심이기 때문에 Positron을 사용하고 있고, 다음 장에서 Claude Code의 설치 방법을 보겠습니다.
  • 메모
  • 시간: 1분
  • 같은 Claude Code 프로그램. 차이는 실행 위치가 아니라 작업 화면
  • 웹 Code(claude.ai/code): GitHub 저장소를 클라우드 가상 머신에 복제해 작업. 데스크톱 앱 Code 탭은 내 PC 폴더에서 실행
  • 네 줄 모두 한 가지 이유: 에이전트가 돌린 결과를 내 콘솔과 내 데이터 뷰어에서 직접 확인

  • 사례 프로젝트에서: knit 실패 원인 중 하나가 렌더 환경과 라이브 세션의 차이. 세션 공유가 중요한 이유
  • 공정하게: 웹이 나은 경우
    • 설치 없이 바로 시작(R, Positron, 확장, MCP 설정 불필요)
    • 여러 작업을 맡겨 두고 나중에 결과만 받음. 휴대폰에서도 지시 가능

  • 결국 선호의 문제. 나는 분석 작업이 중심이라 이쪽
  • 도구 기능 설명은 발표 1주 전 최신 버전과 재대조(행동 규칙 4)

CLAUDE.md와 스킬의 차이

CLAUDE.md 스킬 (SKILL.md)
읽히는 때 세션마다 항상 요청이 호출 문구와 맞을 때만
담는 것 늘 적용되는 것: 목적, 역할, 정의, 규칙 한 작업의 절차: 순서, 점검표, 출력 형식
개수 프로젝트당 하나 작업당 하나, 여러 개
넣는 기준 모든 작업에 해당하는가 같은 절차를 세 번째 시키는가

사례에서

  • CLAUDE.md: 집계값만 출력, 행 단위 출력 금지
  • SKILL.md: 원고 수치를 데이터에서 다시 계산해 대조
  • 대본
    • 그렇다면 어떤 내용은 CLAUDE.md에 넣고, 어떤 내용은 스킬에 넣어야 할까요?
    • 둘 다 Markdown 파일이고 둘 다 에이전트가 읽지만, 읽히는 때가 다릅니다.
    • CLAUDE.md는 세션마다 항상 읽히고, 스킬은 요청이 호출 문구와 맞을 때만 읽힙니다.
    • 그래서 CLAUDE.md에는 목적, 역할, 정의, 규칙과 같이 늘 적용되는 내용을 넣고, 스킬에는 한 작업의 순서와 점검표, 출력 형식을 넣습니다.
    • 같은 절차를 세 번째 시키고 있다면 그때 스킬로 옮기시면 됩니다.
    • 예를 들어 “집계값만 출력”은 모든 작업에 해당하기 때문에 CLAUDE.md에 둡니다.
    • 이 규칙을 스킬에 두면 그 작업에서만 지켜지고 다른 작업에서는 빠지게 됩니다.
    • 반대로 절차를 CLAUDE.md에 넣으면 파일이 길어져서 뒤쪽의 규칙이 무시됩니다.
    • 정리하면 CLAUDE.md는 모든 작업에 적용되는 규칙이고, 스킬은 한 작업의 절차입니다.
    • 다음은 에이전트가 외부 도구를 직접 부르는 MCP입니다.
  • 메모
  • 시간: 1.5분
  • 메시지 한 줄: 늘 지킬 것은 CLAUDE.md, 시킬 때만 따를 절차는 스킬
  • 둘 다 Markdown, 둘 다 에이전트가 읽음. 차이는 읽히는 때와 범위

MCP: 개념과 역할

2. 작업 환경

개념

  • Model Context Protocol: 에이전트가 외부 도구를 함수처럼 부르는 규격
  • 서버 하나 = 도구 묶음 하나 (PubMed, R 세션)
  • 설정 한 번이면 모든 세션에서 사용

역할과 효과

  • Positron MCP: 내 R 세션에서 실행, 객체 조회
  • 문헌 MCP: 검색, 서지 조회, PDF 확보를 에이전트가 직접
  • 복사, 붙여넣기 단계가 없어짐
  • 결과에 DOI, 출처가 붙어 검증 가능

작성 요점

  • 무엇이 밖으로 나가는지 확인: 검색 질의만 전송
  • 쓰는 도구만 연결. 많으면 어느 도구를 쓸지 헷갈림
  • 권한 allow에 도구 이름 단위로 등록
  • 연결 상태 확인: claude mcp list
  • 대본
    • MCP는 에이전트가 외부 도구를 함수처럼 부를 수 있도록 해 주는 규격입니다.
    • Anthropic이 공개한 규격이며, 다른 에이전트도 지원하고 있습니다.
    • 서버 하나가 도구 묶음 하나에 해당하는데, PubMed 하나, R 세션 하나와 같은 식입니다.
    • Positron MCP를 사용하면 에이전트가 실행한 코드가 제 콘솔에 그대로 찍히며, 앞에서 같은 R 세션을 본다고 말씀드린 근거가 바로 이것입니다.
    • 사례에서는 PubMed MCP로 문헌 24편의 서지를 조회했습니다.
    • 결과에 DOI와 출처가 함께 붙어서 오기 때문에 제가 직접 검증할 수 있습니다.
    • 문헌 검색 MCP를 통해 밖으로 나가는 것은 검색 질의입니다.
    • 다만 에이전트가 읽은 결과가 모델 서버로 간다는 점은 1막에서 말씀드린 것과 같습니다.
    • 연결 상태는 claude mcp list로 확인할 수 있으며, 다음 장에서 사례의 구성을 보겠습니다.
  • 메모
  • 시간: 1.5분
  • 메시지 한 줄: 에이전트가 쓸 수 있는 도구를 늘리는 규격. 데이터는 안 나가고 질의만 나감
  • 개념: Anthropic이 공개한 규격, 다른 에이전트도 지원. 서버는 로컬 프로세스 또는 원격
  • 사례: 문헌 단계(3막 ⑤)에서 PubMed MCP로 24편 서지 조회, Europe PMC로 PDF. allow 항목에 lookup_article_by_citation, get_article_metadata
  • Positron MCP: 에이전트가 돌린 코드가 내 콘솔에 표시됨. 같은 세션을 본다는 것의 기술적 근거
  • 전송 범위: 문헌 MCP는 질의와 결과. 에이전트가 읽은 결과는 모델 서버로 감(1막 에이전트 방식 그림)

AI 활용 논문의 윤리

4. 정리

저자 자격

  • AI는 저자로 올릴 수 없음(ICMJE, COPE 공통)
  • 이유: 정확성, 무결성, 독창성에 책임질 수 없음
  • 저자 기준 4가지(기여, 초안 또는 수정, 최종 승인, 책임)를 AI는 못 채움
  • 감사의 글에도 AI를 사람처럼 적지 않음

사용 공개

  • 투고 시 커버레터에 사용 사실
  • 원고 해당 절에 도구 이름, 버전, 용도(예: 코드 작성, 문장 교정)
  • 문법 교정 수준은 면제하는 저널도 있음. 애매하면 공개
  • 저널마다 위치와 문구가 다름: 투고 규정 확인

최종 책임

  • AI 산출물은 틀리거나 빠지거나 치우칠 수 있음: 저자가 읽고 고침
  • AI 생성물을 1차 출처로 인용 불가. 원 문헌을 인용
  • 숫자는 실행 출력, 인용은 원문과 대조한 기록을 남김
  • 공개하지 않은 사용: 정정 대상, 경우에 따라 부정행위
  • 이해: 내가 설명할 수 없는 결과는 내 이름으로 내지 않음

    • 시드 생성기: 비밀 키 + 직전 토큰 몇 개(슬라이딩 창, 논문 기본 4개)를 해시 → 시드. 같은 키, 같은 직전 토큰이면 같은 시드. 참조 구현은 Threefry 난수기, 63비트 키

    • 품질 보호 2, 반복 문맥 마스킹: 한 응답 안에서 같은 직전 토큰 묶음이 다시 나오면 같은 시드라 같은 방향으로 기울게 됨 → 그 토큰은 워터마크 없이 원래 분포로
    • 품질 보호 3, 적용 순서: temperature, top-k, top-p 조정이 끝난 분포에 적용. 사용자 샘플링 설정과 충돌 없음
    • 실증: DeepMind는 Gemini 응답 약 2천만 건 실험에서 사람 평가 품질 차이 없음. Anthropic 내부 시험도 내용, 창의성, 가독성 차이 없음, 토큰 증가 없어 비용 동일

    • 한계가 원리에서 나오는 이유: 짧은 글은 평균이 우연과 구분 안 됨 / 후보가 하나인 자리(Principia → Mathematica)는 고를 것이 없어 사실, 제목, 수치 많은 글에 희박 / 코드는 정확 출력 필요해 미적용, 주석만 / 편집은 고친 토큰과 그것을 문맥으로 쓰는 뒤 몇 토큰만 깨짐, 전면 재작성과 타 모델 패러프레이즈는 대부분 깨짐 / 사람 글 교정은 Claude가 고른 단어가 적음 / 탐지는 “이 키의 패턴이 있는가”만 답함
    • 키 관리: 키가 새면 누구나 넣거나 지울 수 있음 → 탐지는 API로만, 자격 기관 한정
    • 외부 검증: 2026-09 arXiv 논문(Nemecek 외), 공개 구현을 오픈 모델에 적용. 산문은 시드 변경 수준의 영향, 코드는 한 모델에서 정확도 3점 손실, 탐지는 우연 수준. 배포된 Claude 자체는 검증 불가라는 점을 거버넌스 문제로 지적
